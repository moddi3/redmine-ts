`people_find` is a new read-only workflow tool that finds people by name and returns each one's id, name and login, which an `@login` mention takes. It works with any API key. With `project_id` it searches the project's members. With `issue_id` it also searches the issue's author, assignee, watchers and journal users, and `found_as` says where it found each person, so someone on the issue who is not a member of its project shows without `member`. Words match in any order, ignoring case and accents, and a word may be the start of one, so `petrov ivan` and `Iv Pet` both find Ivan Petrov. Groups are not matched. It returns at most 10 matches, each with its login from `users_get`, counts the rest in `more`, and sends at most 16 requests. A login that `users_get` may not read, such as a locked user's for a key that is not an admin's, is `null`, and `unavailable` says why. Every access mode lists it, so `full` now lists 93 tools, 92 on a 6.1 server, `no-delete` 77 and `read-only` 44.

The 14 tools whose Redmine actions run `require_admin` on 6.1 and 7.0 now say "Needs an admin key" in their description and in their 403 error: `users_list`, `users_create`, `users_update`, `users_delete`, `groups_list`, `groups_create`, `groups_update`, `groups_delete`, `groups_add_user`, `groups_remove_user`, `groups_remove_users`, `custom_fields_list`, `projects_archive` and `projects_unarchive`. Before, the 403 said only that the key's user lacked the permission. `users_list` now points to `people_find`, or `memberships_list` and then `users_get`. `users_update`, `groups_list` and `custom_fields_list` name what works without an admin key too. The server still lists these tools for every key. Inputs named `user_id` now name `people_find` as where to find the id.

`reference_data` and `issue_context` read at most 5 pages of a project's members. Before, a project of more than 500 members cost a sixth request to learn that more followed.
