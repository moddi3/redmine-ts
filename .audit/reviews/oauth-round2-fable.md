## New findings

### N1. Reuse detection ends a legitimate sign-in when the client refreshes the same token twice at once (medium: availability and interoperability; no confidentiality impact)

- **Where:** `server.ts:672-685` (`refresh`: `has` before Redmine, `consume` after, `reused()` on a failed consume); `server.ts:606-615` (`redeemCode`, same shape); `server.ts:618-622` (`reused` ends the family unconditionally).
- **Scenario:** Two processes of one client share a token store and both see the access token expire: two Claude Code sessions, two VS Code windows, or a hosted client running parallel tool calls in one turn. Both send the same refresh token within the same second. Both pass the `has()` pre-check, both reach Redmine (Doorkeeper keeps the old refresh token valid until the new access token is first used, as the README itself says, so both succeed upstream), the first `consume()` wins, the second returns false and `reused()` ends the family. The winner's fresh tokens are refused from then on: the user is signed out and must go through the browser again. Access-token lifetimes are a fixed hour, so expiry is a synchronized event across a client's processes, which makes the race more likely than it looks. The same happens to a client that retries a code exchange that timed out: probe P2. This is the known failure mode of strict rotation; Auth0, Okta and others add a short reuse window for it, and RFC 9700 §4.14.2 does not forbid one.
- **Confirmed:** probe P1, three variants. API-key mode: statuses 200 and 400 ("every token from this sign-in is ended"), then the 200's access token answers 401. Redmine mode with a Doorkeeper-like upstream that honours the old refresh token: same. P2 (concurrent code exchange, API-key mode): same. Which real clients race themselves is reasoning, not measured.
- **Fix:** Treat a second use that arrives inside a short window after the first as concurrent, not stolen. With the existing interface: on a successful `consume("refresh:<id>")`, also `consume("recent:<id>", 30)`; in both the pre-check and the post-call branch, when the marker is live, answer `invalid_grant` without ending the family (or, as Auth0 does, issue a fresh pair). Keep ending the family outside the window. Document the window. Alternatively, consume before the upstream call for refresh, which closes the race but reopens L4 for refreshes. The same `recent:` marker fixes the code-exchange case.

### N2. Dynamic registration refuses `client_secret_basic` and `client_secret_post`, which RFC 7591 makes the default when the field is omitted (low: interoperability)

- **Where:** `clients.ts:143-150`, `publicClient()` at `:213-215`.
- **Scenario:** A client that writes `token_endpoint_auth_method: "client_secret_post"` into its registration by habit, without reading `token_endpoint_auth_methods_supported`, gets 400 `invalid_client_metadata` and cannot connect. One that omits the field is accepted, although RFC 7591 §2 says an omitted method means `client_secret_basic`; the two cases are the same request and are treated differently. For registrations, unlike metadata documents, the server is the registrar and RFC 7591 §3.2.1 lets it replace requested values; the response's `token_endpoint_auth_method: "none"` is what the client must use, and the MCP TypeScript client honours it (`selectClientAuthMethod` in `@modelcontextprotocol/client` picks the method from the registration response and the server's supported list). The Codex finding 6 argument, that a declaration cannot be silently rewritten, holds for immutable metadata documents, not for a registration the server itself issues. The hosted claude.ai connector picks its method from the server's `token_endpoint_auth_methods_supported` ([anthropics/claude-ai-mcp#1043](https://github.com/anthropics/claude-ai-mcp/issues/1043), closed as not planned) and this server advertises only `none`, so claude.ai is not affected; ChatGPT registers with `none` ([OpenAI forum](https://community.openai.com/t/mcp-with-oauth-dynamic-registration-chatgpt-registers-with-token-endpoint-auth-method-none-but-still-expects-a-client-secret/1366118)); Claude Code's document declares `none`. The risk is the long tail of clients.
- **Confirmed:** probe P4: `client_secret_post` and `client_secret_basic` registrations answer 400; omitted and `none` answer 201.
- **Fix:** For registrations only, accept `client_secret_basic` and `client_secret_post` (and omitted) and answer `token_endpoint_auth_method: "none"`, as before this delta; keep refusing key-based methods (`private_key_jwt`, `tls_client_auth`), whose holders expect to prove possession. Keep the refusal for metadata documents.

### N3. A registration with an empty or over-long `client_name` is refused outright, where it was dropped before (low: interoperability)

- **Where:** `clients.ts:49` (`Registration.client_name` lost the `.catch(undefined)` that `Document.client_name` at `:40` keeps).
- **Scenario:** A client that sends `client_name: ""` or a name over 100 characters (a hostname-decorated name is enough) gets 400 for the whole registration. Before this delta the name was dropped and the registration succeeded. The limit itself is right (I4); refusing instead of trimming is the regression.
- **Confirmed:** probe P4 (`emptyName`, `longName` → 400).
- **Fix:** restore `.catch(undefined)`, or truncate to 100 characters.

### N4. The API-key attempt limit does not slow a key oracle (low; the remaining half of L6)

- **Where:** `server.ts:133, :449-455`.
- **Scenario:** Every `GET /authorize` yields a new chain of five checks. An attacker with a list of candidate keys needs one GET per five POSTs: probe P7 measured 15 checks for 18 requests. Each check still costs Redmine one `/users/current.json` with an 8 s timeout, with no concurrency cap and no per-source limit. The README says it "is not a rate limit across sign-ins", so this is documented, but the comment's claim that it "keeps the page from being a fast oracle" is not borne out.
- **Confirmed:** probe P7.
- **Fix:** A real cap needs either the source address or global state. Cheapest with what exists: a global in-flight cap on `checkApiKey` (say 4 concurrent, 503 above it) and a per-browser-nonce counter in the store (`consume("keytry:<nonce>:<n>", 3600)` up to N per hour; the nonce cookie lives an hour and the attacker must drop it to reset, which at least costs a new cookie and is visible). For a per-address limit, accept an optional `clientAddress(request)` hook from the embedder or trust a configured proxy header, and document that the CLI behind a proxy should rate-limit `POST …/oauth/authorize` there.

### Informational

- **I-1. A throwing store fails closed but ungracefully.** Probe P3: with a store whose methods reject, an MCP request with a valid token answers 500 (the gate maps the non-OAuth error through `bearerAuthChallengeResponse`), and the token endpoint and the consent `POST` reject the handler's promise, which `toNodeListener` turns into a 500 and an `onError` call (`node-http.ts:40-45`); Bun and Workers answer their own generic 500. Nothing is admitted. The token endpoint could instead answer `{"error":"temporarily_unavailable"}` with 503 so clients retry rather than drop tokens, and the consent page could say "try again".
- **I-2. Mixed deployments silently lose rotation.** Probe P9: a refresh token issued by an instance with a store, refreshed by an instance without one that shares the secret, renews twice with no `until` cap. Sharing a secret across differently configured instances is an operator error; a sentence in the Grant store section ("every instance, or none") would close it.
- **I-3. Memory store growth is by design.** Each refresh adds a 30-day `refresh:` marker and each family end a 30-day `family:` marker; roughly 720 entries per active client per month. Fine for the CLI; worth a sentence for embedders who pick `memoryGrantStore()` for a busy server. The markers cannot be shorter: they must outlive the token they mark, which lives 30 days from issue.
- **I-4. The Durable Object adapter costs one object call per MCP request** (`families.has("family:…")` in `verify()`), plus one object per key. Correct (the input gate makes get-then-put atomic, as the README comment says); the per-request latency is worth noting next to the example.
- **I-5. A double-click on Allow can land on "already sent".** The page has no script (CSP `default-src 'none'`), so the button cannot disable itself; a slow connection lets a second submit race the first 303. Cosmetic; the person restarts from the client.
- **I-6. Unknown-only scopes now end at an error page.** Clients built on the MCP SDKs derive `scope` from the 401 challenge or `scopes_supported`, both ours, and claude.ai sends none by default, so no known client is affected; a client with a hard-coded default such as `openid` would fail at `authorize` with a page the client never sees. The behaviour is per spec (`invalid_scope`); keep it, but it is the one place a future "client X cannot connect" report should look first.
- **I-7. Five Redmine timeouts end a sign-in.** `unreachable` counts as an attempt (`server.ts:449`). Harmless, and arguably right (it bounds load during an outage), but the error page blames the person ("Too many keys were tried").

## Checked and found sound

**Grant store and its use.** Two operations, `consume(key, ttl)` and `has(key)`, on prefixed keys `consent:`, `state:`, `code:`, `refresh:`, `family:`; ids are 32 random bytes from `crypto.getRandomValues` (`seal.ts:120-122`), so keys cannot be guessed or collide across namespaces. `once` and `families` are the same object when a store is given (`server.ts:255-257`), so single use and family checks never disagree within an instance. Marker TTLs outlive what they mark: `code:` 60 s from use (code expires 60 s from issue), `state:` and `consent:` 600 s from use, `refresh:` and `family:` 30 days from use, each ≥ the remaining life of the token. Re-rendered consent pages get a new id and the remaining TTL (`:466-467`), so an answered page is spent even when the next one is not. The memory store's sweep and `live` agree (`until > at` vs `end <= at`), and its concurrency guarantee holds trivially in one process. Family end is idempotent and cannot be extended by repeated ends.

**Atomicity and fail-closed behaviour.** Every store call is awaited on the request path; a rejection propagates and nothing issues (probe P3). A family end that races a refresh already past its family check still yields dead tokens: `verify()` refuses the access token and the next refresh is refused before Redmine (`:675-677`). A code of an ended family cannot be first-exchanged, because ending needs a reuse of that family's code or refresh token, which implies the code was used. The one place the has-then-consume ordering bites is N1, and it bites toward refusal.

**Access-token revocation coverage.** The only path that opens an access token is `verifier.verify` (`server.ts:809-822`), reached through `bearerGate.authenticate` for every method on the endpoint (POST, the SSE GET and session DELETE all go through `endpoint()` in `http.ts:178-200`); the API-key header branch never opens a token. Tokens from an external `verifier` are the embedder's. Family revocation is checked there when a store exists; without one, families are not checked, which the README states.

**Single-use consent and the attempt counter.** Nonce (cookie) and `Origin` checks precede consumption (`:390-407`), so a replay from another browser does not burn the victim's page; the counter is sealed, so it cannot be forged or reset short of a new `GET`; a wrong decision cannot be re-submitted (probe P5). Lockout of another user is impossible: the chain is the attacker's own.

**Fail-closed metadata fetch.** Creation throws without `fetchClientMetadata` (test); the type requires it; the CLI passes `publicFetch`; the contract test and README examples pass it; a non-200 says only "could not be fetched" (test). The `publicFetch` transport now survives any response it cannot represent (test with an asynchronous fake socket).

**Pre-decision errors.** No redirect before a decision; `decide()` and `callback()` are the only redirectors and both sit behind the cookie binding and single use.

**Regressions.** Header mode: `http.ts:188-193` takes `X-Redmine-API-Key` first and never enters the bearer gate; its tests still pass; the only `http.ts` changes are the Bearer regex inside the gate and the canonical-URL check, which runs only when `publicUrl` is set, a branch-new option. Workers: the new code uses `Map`, `Date.now()` and `findLastIndex` only; the default per-isolate memory store and the Durable Object adapter are documented; `fetchClientMetadata: (input, init) => fetch(input, init)` keeps the unbound-fetch rule. Real clients: claude.ai (document, or registration with `none` chosen from the server's list), ChatGPT (`none`), Claude Code (document declaring `none`, loopback redirects under 256 characters), VS Code (document) and Cursor (registration, loopback) pass the new registration and Bearer rules as far as public reports show; what none of them is immune to is N1. Unchanged from round 1 and not re-tested here: a client whose redirect URI uses a custom scheme is refused at registration.

**Docs.** The README's Grant store, Sign out and revoke, API key sign-in and Workers sections match the code, including the 30-day end without a store, the "already sent" behaviour, the `allowedClientHosts` caveats and the corrected Cloudflare flag rationale. The changeset and roadmap match.
