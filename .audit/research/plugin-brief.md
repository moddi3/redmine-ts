# A Redmine plugin that serves MCP at the tracker's own address: research brief

Date: 2026-10-23. Scope: research only. Nothing in `/Users/moddi3/projects/redmine-ts` was changed. The source clones and the throwaway Docker spikes lived in the session scratchpad. "Probed" means I ran it myself: three throwaway `redmine:7.0` containers (7.0.2, Rails 8.1.4, Doorkeeper 5.8.2, Puma 8.0.2, Rack 3.2.7) carrying a scratch plugin mounted read-only. They were deleted afterwards, and the three long-running harness containers were not touched. The sources are listed at the end and cited as `[tag]`.

## Summary

1. **The idea is not new, and the native-Ruby niche is crowded.** I found six Ruby plugins that serve MCP from inside Redmine: five dedicated ones (four created between March and September 2026, one in December 2024) and `redmine_ai_helper`, an older AI suite that added an MCP endpoint. The closest, `joaoperfig/redmine_mcp_plugin`, mounts `POST /mcp`, publishes RFC 9728/8414 metadata at the origin root, uses Redmine's own Doorkeeper tokens, scopes and permissions, offers optional dynamic registration, and pins the official Ruby SDK. It has 16 tools. Only a 3-commit plugin (wendingyuan) claims breadth close to ours (95 tools, through a REST loopback catalog); the OAuth-capable ones have 16 or fewer. Redmine core also has an open request for an MCP server (#42689), so upstream may one day ship one.
2. **Mechanics are friendly.** On 6.1 and 7.0 a plugin's `config/routes.rb` is evaluated at the end of Redmine's own route draw. Origin-root paths such as `/mcp` and `/.well-known/oauth-protected-resource/mcp` work; I probed both. ActionController::Live SSE streams event by event under Puma. Redmine's API authentication (API key, Doorkeeper bearer, Basic) is reusable, but a plugin must skip CSRF and issue its own `Bearer` 401 challenge, because `require_login` sends a `Basic` challenge.
3. **A subpath Redmine (`/redmine`) breaks the root-level well-known paths.** A plugin cannot serve `/.well-known/...` at the origin root when Redmine lives under `/redmine`: I probed 404 at the root and 200 under `/redmine`. The operator must add a proxy rule, or the metadata must be reachable another way (`resource_metadata` in the 401 challenge, and the OIDC "path appending" discovery URL, both of which stay under the prefix).
4. **Doorkeeper is the constraint on option (c), and it is temporary.** Redmine 6.1 and 7.0 pin `doorkeeper ~> 5.8.2` and trunk pins `~> 5.9.6`. Doorkeeper 6 (rc2 on 2026-09-24) adds RFC 8414 metadata, RFC 9207 `iss`, RFC 8707 `resource` with audience, and, on main only, Client ID Metadata Documents. A plugin cannot bump Doorkeeper because it cannot change Redmine's Gemfile pin. Until Redmine adopts Doorkeeper 6, a plugin that makes Redmine a compliant authorization server must rebuild those features in Ruby on a Doorkeeper that lacks them. It would then be a second security-critical OAuth server, next to the TypeScript one.
5. **A plugin does not fix #44271.** Issue edits ignore token scopes in Redmine's `Issue` model (`user_tracker_permission?` checks roles only, unchanged in trunk today). The REST API shares that model, so any option that reaches Redmine through REST inherits the gap. Only a native tool layer that checks scopes itself, or a core patch, sidesteps it. The access modes stay the write guard.
6. **A thin proxy plugin is nearly redundant with a web-server rule.** `location /mcp { proxy_pass ... }` gives the same address with no Ruby. Installing a plugin needs shell access and a restart, which is about the same access as editing the proxy. A proxy plugin also adds a deadlock risk: a Redmine worker held by the proxied request while the sidecar calls back into the same Redmine needs a second worker (reasoned from the worker model, not tested).
7. **Recommendation:** do not build a plugin now. Ship the same-origin deployment as a documented recipe, and make the OAuth work plugin-ready with the cheap hooks in section 4. Revisit when Redmine adopts Doorkeeper 6, when Redmine core ships an MCP server, or when a real deployment cannot use a proxy. If a plugin is built later, it is the thin kind (option b), with Redmine as the authorization server (option c, much smaller once Doorkeeper 6 lands). It is not a native Ruby tool layer. The draft roadmap entry is in section 5.

### 1.3 What the prior art teaches

- **Native plugins converged on the same shape.** A top-level `POST /mcp`, `GET` and `DELETE` answering 405, Redmine's Doorkeeper as the authorization server, a settings page, and permission checks through `User#allowed_to?`. This is the design our option (a)+(c) would copy.
- **Tool breadth is the gap.** The two OAuth-capable plugins have 16 hand-written tools; the 95-tool plugin gets there only through a REST loopback catalog. This matters because our tool layer is catalog-driven.
- **Pitfalls others hit.** `doorkeeper-openid_connect` binds Doorkeeper's controllers at boot before Redmine configures `base_controller`, so joaoperfig loads it lazily and the file says "`require: false` is load-bearing" ([p-joao]). daxonet's in-memory sessions fail under multi-process servers. The Ruby SDK is exact-pinned because its minor releases change the wire.
- **Upstream interest.** Redmine feature #42689 "MCP Server" is open, with no assignee and no target version, and cites runekaagaard as precedent ([rm-42689]).
- **Maintenance is young and thin.** Three of the five dedicated plugins have fewer than 20 commits, and the five have 0–9 stars. This is relevant to "contribute to one rather than write another".

## 2. Redmine plugin mechanics, 6.1 and 7.0

Redmine 6.1: Rails 7.2.4, Ruby 3.2–3.4, `rack >= 3.1.3`. Redmine 7.0: Rails 8.1.4, Ruby 3.2–4.0. Both pin `doorkeeper ~> 5.8.2`; trunk pins `~> 5.9.6` ([rm-gemfile70], [rm-gemfile61], [rm-gemfile-master]). The plugin loader is byte-identical on 6.1-stable and 7.0-stable ([rm-loader]).

### 2.1 Layout and loading

- **Plugins are not Rails engines.** `Redmine::PluginLoader` globs `plugins/*`, pushes each plugin's `app/*` and `lib` into the main Zeitwerk loader (`Rails.autoloaders.main.push_dir`), and runs each `init.rb` inside a `to_prepare` block ([rm-loader]). `init.rb` calls `Redmine::Plugin.register :id do ... end` with `name`, `version`, `requires_redmine version_or_higher: '6.1.0'`, `settings default:, partial:`, `permission`, `menu` ([rm-plugin]). A plugin's `lib/` constants follow Zeitwerk naming rules, so `lib/redmine_mcp/foo.rb` must define `RedmineMcp::Foo`.
- **Order matters for Doorkeeper.** In `config/initializers/30-redmine.rb` the sequence is: a `to_prepare` for `Redmine::Preparation`, then `Redmine::PluginLoader.load` (which registers the `to_prepare` that runs every plugin's `init.rb`), then another `to_prepare` that calls `Doorkeeper.configure` ([rm-init]). So a plugin's `init.rb` runs before Redmine's Doorkeeper configuration, and a second `Doorkeeper.configure` replaces the whole configuration. A plugin therefore cannot adjust Doorkeeper settings (such as `custom_access_token_attributes`, scopes or PKCE) from `init.rb`. It can prepend modules onto Doorkeeper's controllers and models, which is what daxonet does, or re-run the full configuration later, which is brittle. I did not test either from a real plugin.
- **Gems.** Redmine's root Gemfile globs `plugins/*/{Gemfile,PluginGemfile}` ([rm-gemfile70], lines 132–135). So a plugin can add gems (`mcp`, `json_schemer`, `rack-proxy`), but Bundler must resolve them against Redmine's pins. The official Docker image's entrypoint runs `bundle check || bundle install` for plugin gems and runs `rake redmine:plugins:migrate` only when `REDMINE_PLUGINS_MIGRATE` is set ([docker-entry]).
- **Install steps** are copy or clone into `plugins/`, `bundle install`, `rake redmine:plugins:migrate`, restart; uninstall is a migrate to `VERSION=0`, removal, restart. A plugin's `init.rb` is not reloaded per request ([rm-wiki-plugins], [rm-wiki-tutorial]).
- **Licensing.** Redmine's source headers say GPL "version 2, or (at your option) any later version" ([rm-loader]). The Ruby SDK is Apache-2.0 ([ruby-sdk]), which is compatible with GPL-3.0 but not GPL-2.0-only; with the "or later" grant that is workable. The existing plugins are GPL-2.0, AGPL-3.0, MIT (haru) and unlicensed. Our packages are MIT. I did not find an authoritative statement that a plugin must be GPL, and this is not legal advice; an owner who wants a plugin should decide the license deliberately.

### 2.2 Routes, including `/mcp` and the origin-root `/.well-known`

- Each plugin's `config/routes.rb` is `instance_eval`'d at the **end** of Redmine's own `routes.draw` block, after all core routes and the Doorkeeper routes ([rm-routes70], lines 433–439; 6.1-stable lines 430–435). Redmine has no wildcard route, so plugin routes win only where core defines none; `/mcp` and `/.well-known/*` are free. The tutorial says plugins must declare every route they need ([rm-wiki-tutorial]).
- **Probed (7.0.2, Redmine at root):** a plugin with `get '/.well-known/oauth-protected-resource/mcp'`, `get '/.well-known/oauth-authorization-server'` and `post '/mcp'`, all with `format: false`, answered 200 for each. Core's `use_doorkeeper` mounts `/oauth/*` ([rm-routes70], line 21); it serves no `/.well-known`.
- **Subpath, probed.** I ran the same plugin in a container with `RAILS_RELATIVE_URL_ROOT=/redmine` and the repo harness's `config.ru` `map`:

  | Request                                                                                                        | Result     |
  | -------------------------------------------------------------------------------------------------------------- | ---------- |
  | `/.well-known/oauth-protected-resource/mcp` (origin root)                                                      | 404        |
  | `/redmine/.well-known/oauth-protected-resource/mcp`                                                            | 200        |
  | `/redmine/.well-known/oauth-protected-resource/redmine/mcp` (the RFC 9728 form for `https://host/redmine/mcp`) | 404        |
  | `/redmine/oauth/applications` (Doorkeeper)                                                                     | 302, works |

  Session cookie there: `_redmine_session=…; path=/redmine; httponly; samesite=lax`. Redmine's `config/application.rb` sets the key `_redmine_session`, `path: config.relative_url_root || '/'` and `same_site: :lax` ([rm-app]). The documented subpath setups are `RAILS_RELATIVE_URL_ROOT`, or `Redmine::Utils.relative_url_root`, plus a `map` in `config.ru`; Redmine's stock `config.ru` has no `map` ([rm-wiki-suburi]). A plugin must build every absolute URL from `Redmine::Utils.relative_url_root` and not from `request.base_url`: my scratch metadata used `request.base_url` and so omitted `/redmine` from the issuer. joaoperfig's controller does it correctly ([p-joao]).

- **Consequence for the RFC 9728 well-known path.** For a resource at `https://host/redmine/mcp` the spec's inserted form is `https://host/.well-known/oauth-protected-resource/redmine/mcp`, outside the Rails app. The spec lets a server pick either mechanism, and clients must prefer `resource_metadata` from the 401 `WWW-Authenticate` header ([spec-disc]). So the 401 challenge can point at a URL inside the prefix, and that is the only plugin-only way to serve a subpath install. The Ruby SDK's metadata middleware derives the root form from `resource`, but its transport and Rack middleware also take `resource_metadata_url:` "when the document is served elsewhere" ([ruby-auth]).
- **Consequence for authorization-server metadata.** For an issuer with a path (`https://host/redmine`), a client must try, in order: `/.well-known/oauth-authorization-server/redmine`, `/.well-known/openid-configuration/redmine`, then `/redmine/.well-known/openid-configuration` ([spec-disc]). The third is inside the mount, so a plugin can serve it, but Doorkeeper 6's own metadata route is the root-only `/.well-known/oauth-authorization-server`, and its changelog warns that a path-bearing issuer is not discoverable through that route ([dk-changelog], #1849). The plugin must add the appended OIDC-style alias itself.

### 2.3 Authentication inside a plugin controller

From `application_controller.rb` on 7.0-stable ([rm-appctl]) and probes:

- `before_action :api_session, :session_expiration, :user_setup, :check_if_login_required, :set_localization, :check_password_change, :check_twofa_activation` (line 64).
- `find_current_user` looks at the **session first** and only if no session user was found, and the route `accept_api_auth?`, tries the API key (`X-Redmine-API-Key` or `?key=`), then `Doorkeeper.authenticate(request)` (and `user.oauth_scope = access_token.scopes`), then HTTP Basic (lines 132–185). The REST API setting must be on for all of those.
- `api_request?` is `%w(xml json).include? params[:format]` (line 743), and `verify_authenticity_token` runs `super` only unless `api_request?` (lines 43–47).
- **Probed:** a plugin route without a format and with `accept_api_auth :handle` authenticated an API key header (`api_request?` false) but a POST to a controller without `skip_before_action :verify_authenticity_token` got **422**. An invalid bearer token produced no 401 from Redmine; the request continued as anonymous, so a plugin must render its own 401. Per source, when `require_login` does answer an API request without a key it sets `WWW-Authenticate: Basic realm="Redmine API"` ([rm-appctl], line 313), so it never emits `Bearer` with `resource_metadata`. Every plugin in section 1 renders its own challenge.
- **A cleaner pattern, probed:** route with `defaults: { format: 'json' }`. Then `api_request?` is true, CSRF is bypassed with no `skip_before_action`, with `login_required` on a request without credentials or with a bad bearer got 401, and an API key got 200. Per source the session is not consulted for such a request, so a browser cookie cannot take precedence over the bearer. I did not exercise a real session cookie. The `?key=` query parameter is accepted too (probed), so a plugin that wants header-only keys must reject it.
- **Session and bearer precedence trap.** On a format-less route (the default for the plugins above) a browser's `_redmine_session` wins over a bearer header; joaoperfig solves it with an explicit mode order and a mandatory Origin check ([p-joao], `ARCHITECTURE.md`).
- **OAuth scopes.** `User#oauth_scope=` and `User#allowed_to?` narrow permission checks by token scope ([rm-user]). Doorkeeper's `resource_owner_authenticator` uses Redmine's own session login, so a plugin-hosted authorization endpoint gets Redmine's sign-in, 2FA and sudo mode ([rm-init]).
- **Scope gap #44271.** `Issue#attributes_editable?`, `notes_addable?` and `deletable?` call `user_tracker_permission?`, which checks `roles_for_project` and `permissions_all_trackers?` and never reads the token scope. The method is identical on 6.1-stable, 7.0-stable and master ([rm-issue70], [rm-issue-master]). The #44271 page itself is login-walled ([rm-44271]), and no commit in `redmine/redmine` mentions it ([gh-search]).

### 2.4 Streaming and the app server

- **The MCP transport.** In 2026-07-28 each message is a POST, and the reply is "a JSON object or a request-scoped SSE stream"; the GET stream is gone; servers SHOULD send `X-Accel-Buffering: no` when they open an SSE stream ([spec-http]). Our server answered a 2026-07-28 `tools/list` with `application/json`, and a 2025-era `initialize` with `text/event-stream` plus `x-accel-buffering: no` (probed against the built `redmine-mcp --http`; I did not probe a long tool call). So a proxy must pass SSE through unbuffered for older clients, even though nothing streams for long.
- **Puma (what the official `redmine:7.0` image runs).** The container's main process is `puma 8.0.2` started by `rails server -b 0.0.0.0` (read from the local 7.0 container). **Probed:** `ActionController::Live` in a plugin controller delivered three SSE events one second apart, event by event, directly from Puma. Redmine's middleware (`Rack::ContentLength`, ETag) did not buffer. Rails notes that `Rack::ETag` can buffer on Rack 2.2, and Redmine is on Rack ≥ 3.1.3 ([rails-live], [rm-gemfile70]). Each `Live` request runs in its own thread and holds a Puma thread for its duration.
- **Passenger.** In Nginx and Apache integrations `passenger_buffer_response` / `PassengerBufferResponse` default to off, but Passenger always keeps its own "real-time disk-backed" response buffer; the open-source edition handles one request per process (`passenger_concurrency_model` multi-thread is Enterprise only) and `passenger_max_pool_size` defaults to 6 ([pass-nginx], [pass-apache]). I did not test SSE under Passenger. A long proxied request occupies one of those few processes.
- **Puma's source Gemfile entry** is in the test group; source installs choose their own server (Passenger, Puma, others).
- **Ruby SDK transports.** `StreamableHTTPTransport` is a Rack app mountable in Rails. On the handshake lifecycle its sessions and SSE state live in memory, so it needs a single process (Puma `workers 0`), unless `stateless: true`. The 2026-07-28 lifecycle is sessionless and works with any configuration. The controller pattern calls `render`, which buffers the body, so it cannot serve `subscriptions/listen` and the docs say to pass `serve_subscriptions_listen: false`. Modern-lifecycle requests are served as "SSE-framed single exchanges" even with `enable_json_response: true` ([ruby-transports]).

### 2.5 CSRF, Origin and cookies

- Plugins skip CSRF (`skip_before_action :verify_authenticity_token`) or use the `format: 'json'` default. The five dedicated plugins I read do one or the other.
- The transport spec makes Origin validation a MUST against DNS rebinding ([spec-http]). On a same-origin Redmine mount, a browser's `Origin` equals the Redmine origin; joaoperfig accepts `Origin == request.base_url` plus a settings allowlist ([p-joao]).
- Redmine sets `X-Frame-Options: SAMEORIGIN` and related headers on its responses (seen in my probe). A same-origin consent page of ours would share the origin with Redmine's pages and cookies, so it needs its own `frame-ancestors 'none'` and CSRF token.

### 2.6 Hosted Redmine services

Plugin installation is not an option on every host. This is the reason the standalone server must stay supported.

- **RedmineUP Cloud:** third-party plugins only on the Enterprise plan; other plans can add a custom plugin only "if it already exist in our list" ([rup-faq]).
- **Planio:** its hosting page advertises "a hand-picked set of plugins" ([planio]). An older Planio post on redmine.org says custom plugins go on its Enterprise plan after vetting. That post is from roughly 2010–2016 ([rm-board-hosts]); I could not confirm current terms.
- **Easy Redmine:** its FAQ says compatibility with third-party plugins depends on the plugin and "cannot be guaranteed" ([easy-faq]). I found no cloud custom-plugin process.

## 3. Architecture options

Common ground. The plugin option must still let our TypeScript server run standalone on its own host. All options assume Redmine 6.1+ for OAuth, because Doorkeeper arrives in 6.1 ([oauth-brief]); an API-key-only plugin could reach older Redmine, but our SDK floor is 6.1.

I add a baseline the owner did not list, **(e)**, because every plugin option has to beat it.

### (e) Baseline: no plugin, a documented same-origin proxy

The standalone server runs as a sidecar and the web server routes the Redmine host's `/mcp` (and the OAuth and well-known paths) to it. For example, nginx `location /mcp { proxy_pass http://127.0.0.1:3737; }`, a Caddy `handle /mcp*`, an Apache `ProxyPass`, or an ingress rule. The README already shows Caddy for a separate host. This gives the same address, the full TypeScript tool layer, our own OAuth server federated to Redmine's Doorkeeper, and no Ruby. Subpath Redmine needs two extra rules for the root well-known paths. It needs the hooks in section 4.

### (a) Native Ruby server in the plugin

Redmine models, or a REST loopback, plus the official Ruby SDK.

- **How.** `mcp` 1.8.1 (2026-10-21, Apache-2.0, Ruby ≥ 2.7, depends on `json_schemer`) supports 2026-07-28 and the 2025 handshake versions, stateless mode, a Rails mount or controller integration, and OAuth resource-server pieces: bearer enforcement with RFC 6750 challenges, per-request token verification, a protected-resource-metadata middleware ([ruby-sdk], [ruby-protocol], [ruby-auth]). It documents Doorkeeper as an authorization server. Its verifiers are JWT or RFC 7662 introspection; Redmine's Doorkeeper issues opaque tokens and introspection is off, so a plugin needs a custom `verify(token)` that calls `Doorkeeper.authenticate` in-process, which joaoperfig's `Authenticator` does ([p-joao]).
- **Tool layer, three ways.**
  1. _Hand-written per tool_, as every plugin above except wendingyuan. Fastest to start, widest drift from our TypeScript behavior, 16 tools at best.
  2. _Catalog-driven loopback_, as wendingyuan's 95-tool plugin: a small declarative catalog and a generic REST client against the same Redmine ([p-wen]). It would let us **export our catalog as JSON and interpret it in Ruby**. It still needs a Ruby port of our hand-written parts: the filter grammar, paging, heavy-field trimming, error results, and the six workflow tools (`issue_context`, `reference_data`, `issues_transition`, `attachments_*`, `raw_request`). The loopback needs a free Redmine worker, uses an API key or a forwarded bearer, and inherits #44271 because it goes through REST controllers.
  3. _In-process Rack call_ of the same REST controllers with the user's credential in the environment. Same catalog benefit, no network hop, but Redmine's `find_current_user` accepts only session, API key, bearer or Basic, so it needs a short-lived internal token. I did not spike it.
- **Maintenance.** Highest. A second implementation of ~100 tools and the workflow logic, tracked against Rails 7.2→8.1 and Ruby 3.2→4.0 across Redmine releases. The Ruby SDK shipped eight releases between 2026-08-28 and 2026-10-21, and its 1.8.1 notes say several entries "alter answers on the wire" ([ruby-sdk-releases]); joaoperfig pins the version exactly ([p-joao]).
- **Redmine range.** 6.1+ with OAuth; with API-key-only it could go lower, which we do not need.
- **Security.** Code runs in Redmine's process with direct database access, so a plugin bug is a Redmine bug. In exchange, a native tool can use `Issue.visible` and `allowed_to?` directly, and can check the token's scopes itself (joaoperfig's `ScopeChallenge`), which sidesteps #44271 for its own tools.
- **Deployment burden.** Lowest at run time: one process, no sidecar. Installing needs `bundle install` for `mcp` and `json_schemer` against Redmine's pins, plus a migration for dynamic registration, and a restart. Every Redmine upgrade needs a plugin compatibility pass.
- **UX.** With OAuth through Redmine itself (see (c)) there is one Redmine sign-in and consent hop. API key header clients also work.

### (b) Thin authenticated reverse proxy to a Node sidecar

The plugin routes `/mcp`, checks the request, and forwards to our server on loopback or a private network.

- **Who authenticates.** The plugin, in process, using any of Redmine's own mechanisms. This is the only thing it adds over (e). If instead the plugin forwards everything unauthenticated, it is a worse web-server rule.
- **How identity reaches the sidecar, three ways.**
  1. _Forward the user's bearer._ The sidecar treats it as the Redmine token (the SDK already takes `auth: { bearer }`) and verifies it by calling `GET /users/current.json`, which the OAuth brief probed to work with a bearer ([oauth-brief]). Needs the planned `oauth.verify` seam, and, because the SDK's bearer gate rejects a verifier result without `expiresAt` ([oauth-brief]), a short synthetic expiry. Nothing in the token says it was issued for MCP, so the plugin must accept only tokens of applications flagged as MCP apps, as a substitute for audience.
  2. _Signed identity headers plus a minted token._ The plugin verifies the credential, then forwards `X-Redmine-User-Id` signed with an HMAC (timestamp, method, path, body hash) and a short-lived internal Doorkeeper token for the sidecar to call Redmine with. The sidecar listens only on loopback or a private Compose network and the plugin strips every inbound identity header. Needs a shared secret and rotation.
  3. _Admin key plus `X-Redmine-Switch-User`._ Rejected: it puts an admin key in the sidecar (the OAuth brief's option d1; `application_controller.rb` honors the header for admins, [rm-appctl] line 176).
- **SSE through Rack.** `rack-proxy` 1.0.3 (2026-09-25) "streams by default" and supports Rack 2–3 and Ruby ≥ 3.0 ([rack-proxy]); a Rails controller can also relay with `ActionController::Live` (probed to stream under Puma). Costs: every proxied call holds one Redmine thread or process for the sidecar's whole call; under Passenger OSS the pool is small (default 6). **Deadlock risk:** the sidecar calls Redmine's REST API, which needs a second worker on the same Redmine; with a single-worker Redmine, the proxied request and the sidecar's callback wait on each other. A web-server proxy has no such coupling.
- **Deployment.** The plugin plus a Node 22+ process (systemd unit, or a Docker Compose service on a private network with a secret). That is exactly (e) plus an extra Ruby install.
- **Maintenance.** Low for the Ruby side (a few hundred lines, no tool layer), because the one tool layer stays TypeScript. Redmine range 5.x–7.x for API-key passthrough, 6.1+ for OAuth.
- **Security.** The trust boundary is the header handoff and the sidecar's network position. A spoofable identity header on an exposed port is the classic failure.
- **UX.** Identical to the sidecar-on-its-own-host case once the OAuth question is settled (see (c)); nothing new for any client.

- **Does (c) remove the need for our own authorization server in plugin deployments?** Yes in effect: clients talk to Redmine's Doorkeeper facade, our server is a pure resource server behind the `oauth.verify` seam planned in the OAuth brief, and the sealing key, federation hop and consent page go away. The user signs in once, at Redmine. Tokens appear in Redmine's "Authorized applications" and die when the admin deletes the app. But the OAuth code does not disappear; it moves into Ruby inside Redmine's process, where today's gaps (DCR rows, CIMD fetches from the Redmine host, S256 enforcement, metadata) must be rebuilt on a Doorkeeper 5.8 that lacks them. The standalone TypeScript authorization server must still exist for everyone else. That is two security-critical OAuth implementations to keep current with the spec, with the Ruby one scheduled to shrink when Redmine adopts Doorkeeper 6.
- **Does it fix #44271?** No. The gap is in Redmine's `Issue` model, which REST controllers share, so everything that calls REST (the sidecar, a loopback tool layer) inherits it. A native tool layer can check scopes itself. A plugin could also `prepend` a patch onto `Issue#user_tracker_permission?`, but that silently changes core security semantics. The right fix is upstream; until then the access modes remain the guard, as the OAuth brief says.
- **Audience.** With one logical resource server (Redmine's REST plus `/mcp`), accepting any Redmine token is no wider than that token's own scopes on REST. The residual risks are tokens minted for unrelated OAuth apps, and the spec's MUST on audience validation, which would be a documented deviation until Doorkeeper 6.

## 4. Effects on the current TypeScript work

Nothing here needs a plugin. It keeps (e) cheap now and the plugin options open later. The OAuth brief's v1 scope is the baseline ([oauth-brief], section 5); items marked _must_ are cheap to do while the OAuth code is new and expensive to retrofit.

1. **Mount path and well-known insertion (must).** Today `node-http.ts` answers 404 for everything but `/mcp`, and the handler "serves every path it receives" ([README]); the brief lists the authorization endpoints as `/authorize`, `/token`, `/register` at the root. On Redmine's origin those collide with nothing (`/oauth/*` is Doorkeeper's) but would need separate proxy rules and would break a subpath mount.
   - Take a base path (default `/mcp`; accept both a stripped and an unstripped prefix, since proxies differ).
   - Namespace every OAuth endpoint under it: `<base>/oauth/authorize`, `<base>/oauth/token`, `<base>/oauth/register`, `<base>/oauth/redmine/callback`. Then one proxy rule `location /mcp` carries all of it.
   - Serve authorization-server metadata at all three discovery URLs a client may try for an issuer with a path ([spec-disc]): `/.well-known/oauth-authorization-server/<path>`, `/.well-known/openid-configuration/<path>`, and `<path>/.well-known/openid-configuration`. Only the third needs no root rule.
   - Make the protected-resource-metadata URL in the 401 challenge derivable from configuration and able to point inside the mount, so a subpath deployment does not depend on root rules. Keep serving the inserted well-known form too.
2. **Public URL (must).** `--public-url` already is needed as the `resource` and issuer. Make it carry scheme, host and path (`https://redmine.company.com/mcp`, `https://host/redmine/mcp`). Never derive it from `Host` or `X-Forwarded-*`; the Caddy example in the README rewrites `Host` already. The PRM `resource` must equal the URL the user typed (claude.ai, [oauth-brief]).
3. **Public vs internal Redmine URL (must).** Keep `REDMINE_URL` as the server-to-server base (it can be `http://redmine:3000` or `http://127.0.0.1:3000/redmine`) and add a separate browser-facing `REDMINE_PUBLIC_URL`, defaulting to `REDMINE_URL`, used for the redirect to Redmine's `/oauth/authorize`. Check the SDK against absolute URLs Redmine returns, such as an attachment `content_url`, which Redmine builds from its own host setting and so will carry the public host while the SDK talks to the internal one (the SDK refuses a path outside `REDMINE_URL`, [README]; I did not test this case).
4. **Trusted identity (should; design only).** Do not build header trust now. But shape the planned `oauth.verify(token)` seam so a later `authenticate(request)` can replace it (or add a `trustedProxy` option) without changing the handler contract: a result carrying the Redmine credential (`{ bearer }` or `{ apiKey }`), scopes, an `expiresAt`, and the client ID. Default is to trust no identity or forwarding header, and, for a proxy that terminates auth, to strip inbound ones.
5. **Cookies (must).** Redmine's `_redmine_session` is `HttpOnly`, `SameSite=Lax`, `path=/` (or the subpath) on the same origin as `/mcp` ([rm-app]). Our server must never read it, and the proxy recipe must drop the `Cookie` header before forwarding, or the sidecar receives the user's Redmine session cookie. Name any cookie of ours with the `__Host-` prefix (as the OAuth brief plans) so names cannot collide; note `__Host-` requires `Path=/`, which is the whole origin even under a subpath. The consent page must not depend on any Redmine cookie, and sets `frame-ancestors 'none'`, because Redmine's pages share the origin.
6. **CORS and Origin (should).** On a same-origin mount, browser pages of Redmine itself need no CORS, but our Origin check (merged in PR #17: hostname or exact-origin allowlist, 403 otherwise, [README]) still runs on a browser's `Origin`. Treat the origin of `--public-url` as allowed implicitly, so a same-origin page is not refused; keep every other origin explicit. Credentials stay off.
7. **Subpath Redmine (must test).** The harness already has a `/redmine` subpath container on port 3071 ([compose]). Add a contract test that puts a proxy in front for three layouts (root mount, `/mcp` on the Redmine origin, `/redmine/mcp` on a subpath Redmine) and runs the whole OAuth flow, including the Redmine redirect, which checks every item above.
8. **Redmine 401 mapping (already planned).** Map a Redmine 401 during a request to HTTP 401 `invalid_token`, as the brief says. Under (c) the same mapping handles Redmine's own bearer.
9. **Catalog as a shared artifact (should).** Our tool layer is built at startup from the SDK catalog ([catalog-tools.ts]). Publish a versioned `catalog.json` (name, method, path, input and output schemas, annotations) and a golden `tools/list` snapshot as a conformance suite that any implementation, including a future Ruby one, can be run against. Without that, a plugin's tool list drifts from the standalone server's, and clients configured against one behave differently on the other. It also keeps (a) cheap if wanted, per section 3.
10. **Keep the access modes and scope names (must).** The OAuth brief maps MCP scopes to `redmine:read`, `redmine:write`, `redmine:delete`. Keep the names independent of Redmine's own permission scopes, so the same client configuration works against the standalone server and a plugin.
11. **Avoid:** assuming the server is at the origin root; listing endpoints with fixed root paths; using `request.url` for anything the server publishes; a consent cookie without a prefix; storing anything keyed by the Redmine session.

## 5. Recommendation and draft roadmap entry

**Recommendation.** Do not build a plugin now. Publish same-origin deployment recipes (nginx, Caddy, Apache, Docker Compose sidecar, and Redmine under a subpath) and make the OAuth work plugin-ready with items 1–7 and 9–10 above. Keep the standalone server the one supported product: hosted services (RedmineUP Cloud, Planio) install plugins only on top plans or on request, and six existing plugins already occupy the native niche. If a plugin is wanted later, build the thin kind (d1) and let Redmine be the authorization server (c), not a native tool layer: it keeps one tool implementation, and (c) gets smaller when Redmine adopts Doorkeeper 6. Triggers to revisit:

- Redmine adopts Doorkeeper 6, which brings RFC 8414 metadata, `resource` audiences, `iss` and, on Doorkeeper main, Client ID Metadata Documents.
- Redmine core builds its own MCP server (feature #42689).
- A real deployment cannot put a proxy in front of Redmine but can install a plugin.

Before building anything, run a spike for the open points in "What I could not verify" below.

### Draft entry for `docs/roadmap.md`

```markdown
## Redmine plugin: MCP at the tracker's own address (later)

An organization may want MCP at `https://redmine.company.com/mcp` instead of on a second host. A reverse-proxy rule in front of the standalone server already gives them that address, so the first step is a deployment recipe (nginx, Caddy, Apache, a Docker Compose sidecar, and Redmine under a subpath), not a plugin. For the recipe, the OAuth work mounts every endpoint under one configurable path, takes a public URL apart from `REDMINE_URL`, serves its metadata at each discovery path a client may try, and never reads Redmine's `_redmine_session` cookie. The standalone server stays the supported product, because hosted Redmine services install third-party plugins only on top plans or on request.

A plugin would have to beat that recipe, and the obvious designs do not yet. Five dedicated Ruby plugins, and an AI suite, already put MCP at `/mcp` or nearby, and the closest, `joaoperfig/redmine_mcp_plugin`, has OAuth, dynamic registration and 16 hand-written tools, so a native Ruby tool layer would copy our 92 tools into a crowded niche. A plugin that makes Redmine the authorization server would rebuild, in Ruby and on Doorkeeper 5.8 (pinned by Redmine 6.1 and 7.0), the metadata, `resource` audiences, `iss` and Client ID Metadata Documents that Doorkeeper 6 adds. It would not fix Redmine's #44271 either, since issue edits ignore token scopes inside Redmine's `Issue` model, so the access modes stay the write guard.

Revisit when Redmine adopts Doorkeeper 6, when Redmine core builds its own MCP server (feature #42689 is open), or when a real deployment can install a plugin but cannot add a proxy rule. The plugin would then be a thin Rack proxy with in-process authentication in front of the standalone server, with Redmine as the authorization server, and not a second tool layer. Source: the owner's request, and the plugin research brief in this repository's decision log.
```

### What I could not verify

- **claude.ai and ChatGPT against a Doorkeeper-based authorization server.** I did not run either client against a plugin-served Redmine. The client matrix is from the OAuth brief.
- **Reconfiguring Doorkeeper from a plugin.** From source, `init.rb` runs before Redmine's `Doorkeeper.configure`, so a plugin cannot set `custom_access_token_attributes` or `force_pkce`. I did not test registering a later `to_prepare` or patching the configuration object.
- **A real browser session next to a bearer.** The precedence rules are from source; my probes did not send `_redmine_session`.
- **SSE under Passenger and Apache.** Only Puma was probed. The Passenger statements are from its configuration reference.
- **An in-process Rack dispatch** of Redmine's REST controllers (option a, variant 3) and the SDK's behavior with a public/internal URL split (item 3). Neither was tried.
- **Hosted-service policies.** Current Planio and Easy Redmine terms are unconfirmed. The Planio post is old.
- **#44271.** Its page is login-walled. I confirmed only that the code pattern is in 6.1-stable, 7.0-stable and master, and that no commit in `redmine/redmine` mentions the issue number.
